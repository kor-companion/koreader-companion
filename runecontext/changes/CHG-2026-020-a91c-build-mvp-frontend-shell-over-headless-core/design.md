# Design

## Overview

Implement the MVP user-facing shell after CHG-019 chooses the frontend technology. The design constraints are intentionally framework-neutral so the chosen stack cannot bypass the validated core architecture.

## Required Screens Or Surfaces

- Onboarding and safety explanation for managing e-reader files.
- Device discovery and manual path selection using core-provided host/device state.
- Kobo readiness and support classification.
- KOReader release selection and payload validation summary.
- Install dry-run plan, confirmation, progress, completion, warnings, and rollback guidance.
- Backup creation, backup list, backup detail, and human-readable summary display.
- Restore preview, selection, confirmation, progress, and result reporting.
- Operation logs and recovery guidance.
- Safe sync/eject status and warnings when safe eject cannot be confirmed.

## Architecture Rules

- Consume workflow/domain state from the Rust headless core.
- Display plan items, events, logs, and warnings generated by the core.
- Send commands to the core through the integration boundary selected by CHG-019.
- Keep filesystem writes, path containment, release validation, backup/restore execution, and eject behavior inside the core.
- Treat frontend state as presentation state unless explicitly persisted by the core.

## Trust And UX Requirements

- Show planned reads and writes before confirmation.
- Make backup-before-write visible.
- Use contextual acknowledgements for install, restore, launcher changes, and configuration patching.
- Keep long-running operations responsive and cancellable when the core supports cancellation.
- Surface warnings in plain language, including ambiguous device state, failed validation, failed eject, and partial writes.
- Separate developer setup from end-user install guidance.

## Verification Direction

Frontend tests should prove that user actions call core commands and render core state correctly. They should not mock success by bypassing core validation. Integration tests should cover at least one full dry-run path and one blocked/fail-closed path.
